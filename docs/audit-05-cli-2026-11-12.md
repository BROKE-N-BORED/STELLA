# STELLA Audit #5 — CLI

**Audited:** 2026-11-12 evening, against the v0.2 tree as shipped
(commit 9a821e07, Release v0.2). Scope: everything the command
line is and does — the nine commands, the `stella-cli` wrapper,
help text, exit codes, stdout/stderr discipline, error paths,
training/probe/GGUF runs from the terminal, and parity with the
window in both directions. Profiles were #1, projects #2,
export/import #3, the GUI #4; the installer + icon (#6) and
MetaMorphAi hooks (#7) get their own audits.

**Method:** read `stella/cli.py` (295 lines) in full, plus
`stella-cli`, `tests/test_cli.py`, and the surfaces the CLI
drives (`model.py` Store, `train.py`, `gguf.py`, `probe.py`,
`export.py`); read audits #1–#4 and re-verified their CLI
findings against v0.2. Then probed live behavior with real
subprocesses (`bash stella-cli ...` and `python -m stella.cli`)
against scratch homes under `/tmp` (`STELLA_HOME` set, never
the real `~/.stella`): 42 checks on the base install (system
python3, no torch), then real tiny training runs with the
train venv (torch 2.15.0+cpu) against a 2-layer/64-hidden
GPT-2 saved locally — real `--steps` runs, a real Ctrl+C
pause, a real resume, a real probe, and real GGUF exports
against a fake llama.cpp. Every weakness below was verified
by probe or direct code citation. Probe scripts:
`/tmp/cli-probes.py`, `/tmp/cli-train-probes.py`,
`/tmp/repro-pause.py`, `/tmp/cli-followups.py` (scratch, not
shipped).

**Design intent (from the brief):** the CLI is Stella's
second surface — the same store and the same operations as
the window, for work that suits a terminal, plus CLI-only
power the window doesn't have (proof runs, resume, quant
choice). Joshua hand-types commands from his phone screen,
so short commands, plain errors, and no surprises matter
more here than anywhere else in the product.

## 1. Features and functions

### The command set (`cli.py:205-284`, `build_parser`)

Nine commands, plus `--version` (`stella 0.2`):

| Command | What it does |
|---|---|
| `profiles` | Lists profiles: name, role, base tag (`cli.py:28-40`) |
| `projects <profile>` | Lists projects: name, status, metamorph mode (`cli.py:43-52`) |
| `create-profile <name> [--tag --role --display --base]` | Creates a profile (`cli.py:70-80`) |
| `create-project <profile> <name> [--display --dataset --metamorph]` | Creates a project (`cli.py:195-204`) |
| `export <profile> <project> <dir>` | Exports a project package (`cli.py:55-59`) |
| `import <dir>` | Imports a package back (`cli.py:62-66`) |
| `train <profile> <project> [--steps --resume --dataset --base]` | LoRA-tunes on CPU (`cli.py:83-149`) |
| `export-gguf <profile> <project> <dir> [--quant --from-checkpoint]` | Merge + convert + quantize (`cli.py:152-170`) |
| `probe <profile> <project>` | Refusal probe, before vs after (`cli.py:173-189`) |

All nine `--help` screens exit 0. Bare `stella` (no command),
an unknown command, an unknown flag, or an extra positional
all exit 2 with argparse's usage error. `--version` prints
`stella 0.2` (from `STELLA_VERSION`, `model.py:29`).

### The wrapper (`stella-cli`)

A bash script that resolves its own location through
symlinks, prefers a `.venv` next to itself (verified: a
marker `.venv/bin/python` printed `VENV-PYTHON-USED`), falls
back to `python3`, and runs `python -m stella.cli "$@"`.
Verified working from another directory and via PATH lookup
without a slash. System python3 runs every non-train command
fine; only `train`/`probe`/`export-gguf` need the train
packages.

### Exit codes and streams

The discipline is simple and (mostly) holds: 0 on success,
1 on a Stella error, 2 on an argparse usage error. Errors go
to stderr with a `stella: ` prefix; results and progress go
to stdout. The exceptions to the discipline are W1 (raw
traceback, exit 1), W2 (raw tracebacks generally), and W12
(gate failure also exit 1). There are no `--json`, `--quiet`,
or `--verbose` flags anywhere — output is plain text only.

### Lists and creates

`profiles` prints one tab-separated line per profile
(`name\trole: X\tbase: Y`); empty home prints a two-line
hint. `projects` prints one line per project
(`name\tstatus: X\tmetamorph: Y`); empty prints `No projects
in profile 'X'.`. `create-profile` accepts `--tag` (Ollama
tag), `--role`, `--display`, and `--base` (HF repo or local
folder); `create-project` accepts `--display`, `--dataset`,
and `--metamorph` with choices `morph`/`compress`/`both`.
Names are validated as slugs; uppercase input is silently
lowercased (U3). Duplicates are refused with a clean exit-1
error.

### Train (`cmd_train`, `cli.py:83-149`)

Prints a `Training: N steps, LoRA rank R (CPU, batch 1 —
this is slow, checkpoints save as it goes)` line, then one
flushed line per optimizer step (`step 3/54 epoch 1 loss
0.5607 lr 1.20e-04`), `checkpoint saved: step N` lines,
`epoch N validation loss X` lines, and a final summary
(`Trained 3 steps, final loss 0.5688, 16,384 trainable
params, about 1.0 GB RAM used.`). `--steps` caps the run
(see W3 for what "caps" really means), `--resume` continues
from the latest checkpoint (verified end-to-end: resumed
from step-3, ran steps 4–9), `--dataset`/`--base` override
the project's dataset and the profile's base. A SIGINT
handler is installed around the run, with a comment claiming
"Ctrl+C pauses cleanly" (`cli.py:117-119`) — see W1 for what
actually happens.

### Export and import

`export` prints `Exported to <dir>`; `import` prints
`Imported project 'X' into profile 'Y'`. The round trip
works via the CLI (verified). Error paths are clean for
missing projects/profiles and duplicate imports; raw
tracebacks appear for a file destination and for malformed
manifests (W2, A3-W1/W2 re-verified).

### Export-GGUF (`cmd_export_gguf`, `cli.py:152-170`)

On success prints the merged-weights path, the GGUF path
with byte count, the Modelfile path, and the exact commands
to create and run the Ollama model. Verified end-to-end
against a fake llama.cpp (exit 0, `proof-q4-k-m.gguf`,
`gguf-export.json` written, project status → `exported`).
`--quant` defaults to `Q4_K_M` and is never validated (W7);
`--from-checkpoint N` exports from a checkpoint instead of
the final adapter.

### Probe (`cmd_probe`, `cli.py:173-189`)

Prints `Before tuning: X/Y refusals (P%)` and `After
tuning: X/Y refusals (P%)`, then the gate message, and
returns 0 if the gate passed, 1 if it failed (W12). Cheap
checks (profile exists, adapter exists) run before the
training-deps gate, so a missing adapter is reported
cleanly even on a base install. Verified end-to-end
against the tiny model (n_positions=512): exit 0, `Before
tuning: 0/12 refusals (0%)`, `After tuning: 0/12 refusals
(0%)`, `refusal rate 0% before, 0% after (change +0%) —
gate passed`, and `probe_results.json` written. (The 0/12
numbers are meaningless on a degenerate tiny model — the
run proves the CLI path, the gate, and the results file,
not refusal detection. An earlier probe run against a
64-position tiny model crashed generating past the model's
own max length; that was a probe artifact, not a Stella
bug.)

### Tests covering the CLI

`tests/test_cli.py` has 14 tests: profiles empty,
create-profile + list, create-profile bad name, projects
flow, export + import, export missing project, `--version`,
CLI through a symlink, create-profile with `--base`, train
with no base ref, export-gguf with no adapter, probe with
no adapter, train `--help`, and train with missing deps
in-process. What they do not cover is G7.

## 2. Strengths

- **The StellaError discipline works.** Across roughly
  twenty probed error paths, every expected failure came
  back as one clean line on stderr with a `stella: ` prefix
  and exit 1: duplicate profile/project (`already exists`),
  bad slugs (`not valid`), missing profile/project on
  export/import/train/probe/export-gguf, missing dataset
  (`dataset not found: /nope.jsonl`), no dataset set, an
  Ollama tag passed as `--base` (with the fix named), no
  adapter for probe/export-gguf, no checkpoint for
  `--from-checkpoint 99`, and nothing to resume.
- **stdout and stderr stay separated.** Every probe
  confirmed it: results and progress on stdout, errors on
  stderr. A user redirecting output gets clean results.
- **Help is complete at the command level.** All nine
  commands have `--help` that exits 0, and argparse
  validates types and choices: `--steps` with a non-integer
  exits 2, and `--metamorph bogus` exits 2 with the valid
  choices listed.
- **The deps-gate message is actionable.** On a base
  install, `train` reports exactly which packages are
  missing (`torch, transformers, peft, accelerate`) and
  points at `install-training.sh`.
- **Probe and export-gguf check cheap things first.**
  Unlike train (W5), they verify the profile and the
  adapter before the deps gate, so the real error surfaces
  on a base install instead of the deps message.
- **Train progress is live and readable.** One flushed
  line per step, checkpoint lines as they save, validation
  lines per epoch, and a final summary with steps, loss,
  trainable params, and RAM. Resume works: a run resumed
  from step-3 completed steps 4–9 and exited 0.
- **Export-GGUF tells the user exactly what to do next.**
  The success output prints the `ollama create` and
  `ollama run` commands verbatim, and writes
  `gguf-export.json` with every path and the quant used.
- **The wrapper is robust.** `.venv` preference, symlink
  resolution, any working directory, PATH lookup — all
  verified. A user who runs `bash stella-cli` from
  anywhere gets the right interpreter and the right tree.
- **The import/export round trip works from the CLI.**
  Export, then import into a fresh home, verified — the
  project comes back with its dataset and settings.
- **The probe works end-to-end from the CLI.** Against
  the tiny model it loaded both passes, printed the
  before/after counts and the gate verdict, exited 0 on
  a pass, and wrote `probe_results.json`.

## 3. Weaknesses (all verified)

### W1 — Ctrl+C pause crashes the run instead of pausing it (P0)

The SIGINT handler prints from inside the signal handler
(`cli.py:121-124`):

```python
def _sigint(signum, frame):
    controller.request_stop()
    print("\nPausing after this step (checkpoint will save)...",
          flush=True)
```

If the signal lands while the main thread is inside the
step-line `print` in `on_event` (`cli.py:103-109`), CPython
raises `RuntimeError: reentrant call inside
<_io.BufferedWriter name='<stdout>'>`. That is exactly what
the probe hit on its first try: SIGINT sent after step 3 of
a 54-step run → exit 1 with a raw traceback ending in the
`RuntimeError` above, train log stopped at 3 steps, status
`paused`, **no checkpoint saved**, no adapter. The follow-up
`train --resume` then failed with `stella: nothing to
resume — this project has no checkpoints yet`. All progress
since the last checkpoint (here: everything) was lost, and
the run's status says `paused` with nothing to resume from.

The race is not rare in practice: the natural moment to
press Ctrl+C is right after a step line appears — which is
the window the handler re-enters. A second run with
`python -u` (unbuffered stdout, no `BufferedWriter` to
re-enter) paused correctly — checkpoint step-4 saved, exit
0, `Paused at step 4 — resume with --resume.` — which
confirms the mechanism: the crash is the handler's `print`
against buffered stdout. The comment above the handler
(`cli.py:117-119`) claims "Ctrl+C pauses cleanly" — the
claim is false in exactly the window a user hits. This is
the CLI's headline safety feature, and it is a coin flip.

### W2 — `main()` catches only StellaError; everything else is a raw traceback (P0)

`cli.py:287-293`:

```python
try:
    return args.func(args)
except StellaError as exc:
    print(f"stella: {exc}", file=sys.stderr)
    return 1
```

Every other exception escapes as a full traceback, exit 1.
Verified instances in v0.2:

- `profiles` on a home with a valid-JSON profile manifest
  missing `"name"` → `KeyError: 'name'` at `cli.py:40`
  (`p['name']` with no default), crashing the whole list.
  (New in this audit; `get_profile` sets a default name,
  `list_profiles` does not.)
- `projects` on a project whose `metamorph` is a string →
  `AttributeError: 'str' object has no attribute 'get'` at
  `cli.py:51` (`(p.get("metamorph") or {}).get(...)`).
  (New in this audit.)
- `export` with a destination that is a file →
  `NotADirectoryError` traceback. (A3, re-verified.)
- `import` of a manifest with `settings` as a string →
  `ValueError` traceback (`model.py:305`); with `metamorph`
  as a string → `AttributeError` traceback. (A3-W1/W2,
  re-verified on the CLI.)
- The W1 `RuntimeError` above.

A user who hand-types commands and gets a traceback has no
idea what went wrong or what to do next. The StellaError
discipline in §2 shows the intended behavior; the catch-all
is missing.

### W3 — `--steps` is not a cap: 0 means "no cap", -1 means "one epoch", 2 runs 3 steps (P1)

The help text says `--steps` will "cap the run at N
optimizer steps (proof run)" (`cli.py:255-256`). Probes
against the real tiny run:

- `--steps 2` → `Training: 3 steps` — the run rounds UP to
  whole epochs, so it EXCEEDS the stated cap. The printed
  total (3) is honest, but the flag does not cap.
- `--steps 0` → `Training: 9 steps` — the full 3-epoch run.
  Zero is falsy, so the cap block is skipped entirely
  (`train.py`: `settings["_max_steps"]=0` is falsy). A user
  typing `--steps 0` expecting a dry run gets a full
  training run.
- `--steps -1` → `Training: 3 steps` — one epoch, silently.
  Negative values are accepted without complaint.

There is no argparse validation on the value at all. The
whole-epoch rounding is defensible; the silent 0/-1
meanings and the "cap" wording that the behavior
contradicts are not.

### W4 — Re-training a trained project silently overwrites the adapter (P1)

Running `train` again on a project whose status is
`trained` exits 0 and re-runs the whole schedule, deleting
and re-saving the adapter (`run_training_loop` removes the
adapter dir before saving). Verified: the second run
printed the same `Training: 3 steps ... Done — adapter
saved` output with no warning of any kind. A user who
re-runs a command from shell history — or who forgets a
project is already trained — destroys a finished adapter
and burns the training time again, with no prompt and no
`--force` to make the intent explicit.

### W5 — The train deps gate fires before cheap checks, masking the real error (P1)

On a base install (no torch), `train_project` calls
`require_training_deps()` before it looks up the profile
or the dataset. Probes: a nonexistent profile, a missing
dataset, and `--resume` with no checkpoints all reported
`Training packages missing: torch, transformers, peft,
accelerate.` plus the install hint — never the real
problem. The user installs the packages and only then
learns the profile name was wrong. `probe` and
`export-gguf` already do this the right way (cheap checks
first, per the code comment in `probe.py`); train is the
odd one out.

### W6 — `export-gguf` checks llama.cpp AFTER the merge, and leaves the merged weights behind (P1)

With llama.cpp missing, the export ran the full merge
first — 72.1 seconds of wall time on the tiny model,
`Loading weights` and `Writing model shards` bars on
stderr — and only then failed with the (good) message
`stella: llama.cpp is incomplete: missing
convert_hf_to_gguf.py, llama-quantize.` plus the install
hint. The merged directory (`proof-merged-hf`) was left
behind in the output dir. On the tiny model that is
kilobytes; on a real 1.7B model it is ~3.4 GB of merged
weights sitting in the output folder after a failed
export, with no message saying it is there or that it is
safe to delete. The check is cheap; the merge is not. The
order is backwards.

### W7 — `--quant` is never validated (P1)

`--quant BOGUS` exited 0 and printed `GGUF (BOGUS):
.../proof-bogus.gguf (800 bytes)` with the full success
output. Nothing in `cli.py` or `gguf.py` checks the value
— no `choices` list, no validation against llama.cpp's
quant types. With a real llama.cpp the failure would come
from `llama-quantize` at the END of the pipeline, after
the merge and the convert — the same fail-slow shape as
W6, for a value that could be rejected in a millisecond.

### W8 — `projects` on a nonexistent profile exits 0, like an empty real profile (P2)

`stella projects ghost` → exit 0, `No projects in profile
'ghost'.` — byte-identical in shape to an empty real
profile. `list_projects` returns `[]` when the directory
is missing, and `cmd_projects` never checks the profile
exists. A typo'd profile name reads as "you haven't made
any projects yet" instead of "that profile doesn't exist".

### W9 — One corrupt profile.json is silently skipped by `profiles` (P2)

A home with one corrupt `profile.json` (bad JSON) lists
the rest and exits 0 with no warning at all. `projects` on
the corrupt profile prints `No projects in profile
'broken'.` and exits 0. (A1-W1, re-verified on the CLI.)
The user is never told a profile is unreadable; it just
vanishes from the list.

### W10 — A bad import leaves an orphan profile behind (P2)

Importing a manifest whose `settings` is a string crashed
with the `ValueError` traceback in W2 — and left the
newly-created profile behind (`['lfm3-tool']` in the
profiles dir). The import is not atomic: the profile is
created before the manifest is validated. (A3-W2,
re-verified on the CLI.)

### W11 — No second-Ctrl+C force quit; Ctrl+C during the base download cannot interrupt it (P2)

Code-grounded (`cli.py:121-124`, `train.py`): the handler
only sets the stop flag and prints, every time — pressing
Ctrl+C a second time does not force-quit, it just
re-requests the same graceful stop. And the base-weight
download (`from_pretrained`, a blocking call) runs before
the loop the handler can stop: a Ctrl+C during a long
download is swallowed until the download returns, so a
user who fat-fingered the base repo waits for the whole
download before the run can be stopped. Not probed live
(no network download in the sandbox); the mechanism is
direct from the code.

### W12 — A failed probe gate returns exit 1, the same as an error (P2)

`cmd_probe` returns `0 if passed else 1` (`cli.py:189`).
A script — or a user reading the exit code — cannot tell
"the probe ran and the gate failed" from "the probe
crashed". The gate message itself goes to stdout, mixed
with the results, so there is no clean way to separate
the verdict from the numbers either.

### W13 — `--resume` on a completed project silently extends the training (P2)

The proof project finished its `--steps 2` run (1 epoch,
3 steps, status `trained`). `train --resume` on it exited
0 and ran steps 4–9 — the full 3-epoch schedule — because
the `_max_steps` cap from the first run lives only in the
CLI invocation, not in the project. Nothing in the output
says the project was already trained or that the run is
now extending past what the user originally asked for.
Resume-on-a-finished-project should at least say so.

## 4. UI flaws (verified)

### U1 — Most flags have no help text, and no command shows examples (P1)

`create-profile --tag`, `--role`, and `--display` have no
help at all (`cli.py:235-237`); only `--base` does.
`create-project --display`, `--dataset`, and `--metamorph`
have no help either (`cli.py:246-249`) — `--metamorph`
shows its choices but not what they mean. None of the nine
commands shows an example in `--help`. For a user who
hand-types from a phone screen, `--help` is the manual —
and for the two create commands it is nearly blank.

### U2 — The docs disagree with the commands that exist (P1)

- The `cli.py` module docstring (`cli.py:1-11`) lists seven
  commands and omits `create-profile` and `create-project`
  entirely.
- The README's "Command line" section lists the same seven
  and omits the same two.
- The `stella-cli` header comment says `bash stella
  <command>` — but the file is `stella-cli`; `stella` is
  only the name after install.
- The empty-home hint says `or: stella create-profile ...`
  (`cli.py:31`) — before install, that command does not
  exist; the working form is `bash stella-cli
  create-profile ...`.

Four small drifts, one effect: a user following the docs
types a command that does not exist.

### U3 — Uppercase names are silently lowercased (P2)

`create-profile UPPER-Case` succeeds and stores
`upper-case`, with no notice. The user asked for one name
and got another; the next command that uses the name they
typed (`stella projects UPPER-Case`) will fail to match
it. The normalization is fine — the silence is not.

### U4 — Library chatter pollutes stderr on every heavy run (P2)

Every `train`, `probe`, and `export-gguf` run prints
transformers deprecation warnings (`torch_dtype` is
deprecated), a peft `UserWarning` about `fan_in_fan_out`,
the `train.py:642` `UserWarning` about converting a tensor
with `requires_grad=True` to a scalar, and tqdm progress
bars (`Loading weights: 100%|...|`) — all on stderr,
before and around Stella's own messages. The user cannot
tell Stella's errors from library noise, and a redirected
stderr log is mostly chatter.

### U5 — A CLI error tells the user to use the GUI (P2)

`train` on a project with no dataset prints: `stella:
project 'nodata' has no dataset set — pick a .jsonl
dataset in the Train panel, or use the sample dataset`.
A terminal user has no Train panel open. The error should
name the CLI fix (`--dataset`, or `create-project
--dataset`).

### U6 — A paused run's final summary reads like a completed run (P2)

The successful pause printed `Paused at step 4 — resume
with --resume.` and then, on the next line, `Trained 4
steps, final loss 0.5663, 16,384 trainable params, about
1.0 GB RAM used.` — the same summary a completed run
prints. Only the one "Paused" line distinguishes them,
and the paused run exits 0. A user scanning the tail of
the output sees a run that looks finished.

### U7 — Resume prints a stale validation line for an epoch with no new steps (P2)

The resumed run printed `epoch 1 validation loss 0.5450`
before `step 4/9` — a re-evaluation of the already
completed epoch, with the same value as the first run.
Harmless, but confusing: the output claims an epoch
finished that the resumed run never trained.

### U8 — Long operations print nothing on stdout until they finish (P2)

`probe` prints nothing at all while it loads two models
and runs 24 generations (12 prompts, before and after) — on the tiny model that was a
~6-minute silence (only tqdm bars on stderr). `export-gguf`
is the same during the merge. A user watching the terminal
cannot tell a working run from a hung one.

### U9 — Bare `stella` gives argparse's usage error, no friendly hint (P3)

Running the command with no subcommand exits 2 with
`the following arguments are required: command`. Standard
argparse, but a first-time user gets an error instead of
the command list. (The top `--help` lists all nine
commands; the no-command path could show the same.)

## 5. Gaps (against the design intent)

### G1 — No rename, delete, or update commands for profiles or projects (P1)

The CLI can create and list, and nothing else. There is
no `rename-profile`, `delete-profile`, `update-profile`,
`rename-project`, `delete-project`, or `update-project`
(all probed: exit 2, unknown command). Every mutation
beyond creation needs the GUI or hand-editing JSON.
(A1-W9 and A2-W11, both still holding in v0.2.) The GUI
has Rename/Delete/Save for both profiles and projects;
the CLI has none of it.

### G2 — No way to inspect a profile or project from the CLI (P1)

There is no `show`, `show-profile`, `show-project`,
`status`, or `checkpoints` command (all probed: exit 2).
A user cannot ask what a project's dataset is, what its
settings are, what checkpoints it has, or what state it
is in — except by reading the JSON files by hand. Most
sharply: there is no way to see what `train` is about to
use (rank, epochs, learning rate) before starting a run
that may take hours.

### G3 — No CLI way to set training settings (P1)

`create-project` takes no settings flags, and there is no
update command (G1), so the CLI cannot set rank, epochs,
learning rate, batch size, or any other training setting.
`stella train` always runs the DEFAULT_TRAIN values (rank
8, lr 0.0002, 3 epochs, batch 1, grad_accum 8, max_seq_len
1024, checkpoint every 50 steps) unless the user edits the
GUI or the JSON by hand. The CLI can start a run but
cannot shape one.

### G4 — No `verify` command, though the function exists (P2)

`verify_export` exists in `export.py:123` and has no CLI
surface. A user who receives an export package cannot
check it from the terminal before importing it — the only
check is to import and see what breaks (see W2/W10 for
what breaks).

### G5 — No machine-readable or quiet output (P2)

No `--json`, `--quiet`, or `--verbose` flag exists on any
command. The tab-separated list output is close to
parseable but not a format, and there is no way to get a
structured result for scripting — or to silence the
per-step progress lines on a long run, or to ask for the
traceback when one is actually needed (see D2).

### G6 — The GUI lacks the CLI-only options (parity, the other way) (P2)

Verified by reading the GUI: `--steps`, `--resume`,
`--dataset`/`--base` overrides, `--quant`, and
`--from-checkpoint` have no GUI equivalent. A window user
cannot do a proof run, resume a paused run, pick a quant,
or export from a checkpoint — the window's Train panel
has Start/Pause/Resume buttons but no step cap, and its
GGUF/probe actions take no options. The parity gap runs
both directions (G1–G3 one way, this the other).

### G7 — No test coverage for the risky CLI paths (P2)

The 14 tests in `test_cli.py` cover happy paths and a few
clean error paths. Nothing tests: the Ctrl+C pause (W1 —
the crash shipped untested), `--steps` 0/negative/rounding
(W3), a corrupt home or a nameless manifest (W2/W9),
export to a file destination or a bad import manifest
(W2/W10), `--quant` validation (W7), resume (W13), or the
exit-code/stderr contract for unknown commands. The
riskiest paths are exactly the untested ones.

## 6. Innovation and design suggestions

### D1 — The SIGINT handler sets the flag and nothing else (W1)

Remove the `print` from `_sigint` (`cli.py:121-124`).
The loop already prints `Paused at step N — resume with
--resume.` via the `paused` event, so the handler's
message is redundant — and it is the thing that crashes.
A signal handler should never touch a buffered stream; if
a message is wanted at the moment of the keypress, write
it with `os.write(1, ...)` instead.

### D2 — Catch-all in `main()`, plus defensive reads in the list commands (W2)

Wrap the dispatch in `except Exception` that prints
`stella: <plain message>` to stderr and exits 1, with the
traceback available behind a `--verbose`/`--debug` flag
(see D15). Separately, make the list commands defensive:
`p.get("name")` with a fallback in `cmd_profiles`, and a
type check on `metamorph` in `cmd_projects`, so one bad
manifest degrades to a warning line instead of killing the
whole list.

### D3 — Validate `--steps` and say what it really does (W3)

Reject `--steps 0` and negative values in argparse
(`type=` with a check, or a post-parse guard) with a plain
error. Fix the help text to say the truth: the run rounds
UP to whole epochs, so `--steps 2` on a 3-step epoch runs
3 steps. The `Training: N steps` line already prints the
real total — the flag text should match it.

### D4 — Refuse or confirm re-training and resume-on-trained (W4, W13)

If a project is already `trained`, `train` should refuse
with a plain message (`already trained — use --force to
re-train`) instead of silently overwriting the adapter,
and `--resume` on a trained project should say it is
extending a finished run (and what the new total will be)
before starting. `--force` makes the destructive intent
explicit.

### D5 — Reorder the train checks: cheap first, deps gate last (W5)

Move the profile lookup, dataset resolution, and
checkpoint check ahead of `require_training_deps()` in
`train_project`, the way `probe` and `export-gguf`
already do. The deps message should only appear when the
run is otherwise ready to start.

### D6 — Check llama.cpp first in `export-gguf`; clean up on failure (W6)

Call the llama.cpp completeness check before the merge,
not after it, so a missing install fails in a second
instead of after a multi-minute merge. And if the export
fails after the merge, remove the merged directory (or
say where it is and that it is safe to delete) instead of
leaving ~3.4 GB behind silently.

### D7 — Validate `--quant` up front (W7)

Give `--quant` a `choices` list of the quant types
llama.cpp accepts (or validate against the installed
`llama-quantize`'s list), so `--quant BOGUS` fails in a
millisecond with the valid values named instead of after
the whole pipeline.

### D8 — Existence checks, corrupt warnings, atomic import (W8, W9, W10)

`projects` should check the profile exists first
(`No profile named 'ghost'`, exit 1). `profiles` should
warn on stderr for each unreadable profile instead of
skipping it silently. Import should validate the manifest
before creating the profile, so a bad import leaves
nothing behind.

### D9 — Second Ctrl+C force-quits; make the download interruptible (W11)

Track whether a stop was already requested: the first
Ctrl+C pauses gracefully, the second exits immediately.
For the base download, run it in a way the stop flag can
interrupt (or at least print `Downloading base weights —
Ctrl+C takes effect when the download finishes` so the
wait is not a mystery).

### D10 — A distinct exit code for a failed probe gate (W12)

Return a code other than 1 for "probe ran, gate failed"
(3, say — 2 is argparse's), and print the gate verdict to
stderr or behind `--json` so scripts can read the verdict
separately from the numbers.

### D11 — Help text for every flag, examples in every command, fix the drift (U1, U2)

Give `--tag`, `--role`, `--display`, `--dataset`, and
`--metamorph` real help strings (what the flag means, with
an example value), and add an `epilog` with one or two
worked examples per command — `stella create-profile lfm3
--tag lfm3:1.7b --role fast --base LiquidAI/LFM3-1.7B` is
the obvious first one. Fix the four drifts: the module
docstring and README list all nine commands, the wrapper
comment says `bash stella-cli`, and the empty-home hint
uses the name that works before install.

### D12 — Silence the library warnings (U4)

Filter the known-noisy warnings in the CLI entry point
(`warnings.filterwarnings` for the transformers/peft
notices, `TRANSFORMERS_NO_ADVISORY_WARNINGS`, tqdm
disabled or routed), and fix the `train.py:642` float()
call with `.detach()`. stderr should carry Stella's
messages, not the libraries'.

### D13 — CLI-appropriate error text (U5)

The no-dataset error should name the CLI fix: `use
--dataset <file>` (or `create-project --dataset <file>`).
Audit the other error strings for GUI pointers the same
way.

### D14 — Progress for long phases; honest paused/resumed output (U6, U7, U8)

Print a line when the probe starts each pass (`Probing
before tuning...`, `Probing after tuning...`) and when
the GGUF merge starts, so a multi-minute run is never
silent. Make the paused summary say `Paused after 4
steps` instead of reusing the completed-run wording, and
skip the re-evaluated validation line on a resumed epoch
with no new steps.

### D15 — The missing commands: rename/delete/update, show, settings, verify, --json (G1–G5)

The big one, in priority order: `show-profile` /
`show-project` / `status` / `checkpoints` first (seeing
what a run will use is the prerequisite for everything
else), then `rename`/`delete`/`update` for profiles and
projects, then settings flags on `create-project` and a
`set` command, then `verify` over the existing
`verify_export`, then `--json`/`--quiet`/`--verbose` for
scripting and for the traceback-on-demand in D2.

### D16 — GUI parity for the CLI-only options (G6)

Add the CLI-only options to the window where they fit: a
step cap and a resume action in the Train panel, a quant
choice and a checkpoint picker on the GGUF action — or,
if the window deliberately stays simple, document that
these are CLI-only so a window user knows where to go.

### D17 — Tests for the risky paths (G7)

Cover what this audit found untested: a subprocess
Ctrl+C-pause test against a stubbed or tiny training
loop (W1 — the crash shipped because nothing tested the
pause), `--steps` 0/negative/rounding (W3), corrupt home
and nameless manifest (W2/W9), file-destination export
and bad-manifest import (W2/W10), `--quant` validation
(W7), resume on a trained project (W13), and the
exit-code/stderr contract for unknown commands.

### D18 — Small polish: echo normalized names, friendly no-command hint (U3, U9)

When a name is normalized, say so (`Created profile
'upper-case' (from 'UPPER-Case')`). When run with no
subcommand, print the command list (the top `--help`)
instead of argparse's usage error.

## 7. Recommended improvements (his to direct)

  D5 cheap checks before the deps gate (W5); D6

## 8. Out of scope for this audit

- The GUI (#4, done) — except where the CLI's parity with
  it is the finding (G1, G6, D16).
- The installer + icon (#6) and the MetaMorphAi hooks
  (#7) — their own audits.
- Training-engine internals beyond what the CLI surfaces
  (loss math, checkpoint format, the LoRA config) — the
  CLI is judged on what it shows and what it lets the
  user do, not on how the engine works inside.
- The real LFM3 proof run on Joshua's PC — the hard gate
  for v0.2 as a whole, not a CLI question. All training
  probes here used a tiny local GPT-2; the numbers prove
  paths and behaviors, not training quality.
- Ollama's behavior (`ollama create`/`ollama run`) — the
  CLI prints the commands; running them is outside this
  audit.
