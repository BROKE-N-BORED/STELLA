# STELLA Audit #4 — GUI (window-level)

**Audited:** 2026-11-12 evening, against the v0.2 tree as shipped
(commit 9a821e07, Release v0.2) — the first audit run against v0.2,
so it covers the main window **and** the v0.2 Train panel. Scope:
everything the window is and does — geometry, the three panes, the
detail panel, the dialogs, the Train panel, the status surface,
error presentation, keyboard behavior, threading, and close
handling. Profiles were #1, projects #2, export/import #3; the CLI
as a whole (#5), the installer (#6), and MetaMorphAi (#7) get their
own audits.

**Method:** read `stella/gui.py` (932 lines) in full, plus
`tests/test_gui.py`, `stella/ollama.py`, and the training-engine
surfaces the window drives (`training_deps_missing`,
`list_checkpoints`, `TrainController`, `train_project`,
`_append_log`); drove the real window offscreen with a counting
fake Ollama server, fake training runs, and fake GGUF/probe jobs;
grabbed and eyeballed screenshots at 1100x680, 900x540, scrolled
to the Train panel, and with the New Profile dialog open. Every
weakness below was verified by probe, screenshot, or direct code
citation. Probe scripts: `/tmp/gui-probes.py`,
`/tmp/gui-probes2.py`, `/tmp/gui-probe-close.py` (scratch, not
shipped); screenshots `/tmp/gui-audit-*.png` (scratch, not
shipped).

**Design intent (from the brief):** one native Qt window, three
panes — profiles left, projects middle, detail right — with the
Train panel in the detail pane from v0.2. The window is the whole
product surface: Joshua works from his phone screen and types
commands by hand, so the window has to be readable, forgiving,
and honest about state at a glance.

**A correction to audit #1:** A1-U3 described the New Profile
dialog as "a separate 420x320 window, not centered on the
parent". That was wrong. It is not a window at all — see W1.

---

## 1. Features and functions

### The window (`gui.py:195-395`, `MainWindow`)

- `QMainWindow`, title `STELLA 0.2 — fine-tune models on your
  PC`, default size 1100x680 (`gui.py:200`), minimum 900x540
  (`gui.py:201`). No window icon is set anywhere (grep: no
  `setWindowIcon`); no geometry persistence (grep: no
  `QSettings`).
- Header label: `STELLA — shape a base model into its proper
  job`, 16px bold. No menu bar, no toolbar, no keyboard
  shortcuts (grep: no `QShortcut`/`setShortcut`).
- Three panes in a `QSplitter`: profiles (left), projects
  (middle), scrollable detail (right). Requested splitter sizes
  `[260, 200, 640]` (`gui.py:270`); panes are collapsible
  (default `childrenCollapsible`).
- Bottom bar: `Export project` / `Import package`, always
  enabled. Status bar is the single status surface (`_say`,
  `gui.py:396`); the v0.1 duplicate-label defect stayed fixed
  (pinned by `test_status_bar_is_the_only_status`).

### Panes and selection (`gui.py:414-505`)

- Profile rows: `Display name [role] — tag`; project rows:
  `Display name — metamorph mode`. New / Rename / Delete under
  each list; all buttons always enabled.
- Selecting a profile loads its projects and its detail fields;
  selecting a project loads its settings, notes, and Train panel.
  The first profile and first project auto-select on refresh.
- The detail panel's tag combo is refilled from Ollama on every
  profile selection (`_show_profile_detail`, `gui.py:481-483`);
  the stored tag is re-added if not installed.
- No double-click action on either list (grep: no
  `itemDoubleClicked`); no tooltips on list items (the only
  `setToolTip` in the GUI is the metamorph combo, `gui.py:322`).

### Detail panel (`gui.py:275-395`)

- Profile form: Display name, Role (bare text field), Ollama
  tag (editable combo), Base ref, Processor; `Save profile`.
- Project form: Display name, Dataset (bare text field),
  Method (`lora`/`full`), LoRA rank (spinbox 1–64), Learning
  rate (free text), Epochs (1–100), Batch (1–32), Max seq len
  (128–32768), MetaMorphAi (combo, the GUI's only tooltip);
  `Save project` writes settings + notes together.
  Non-numeric learning rate is refused with a friendly message
  (`save_project`, `gui.py:560-566`).
- Notes: `QPlainTextEdit`, minimum height 120, below Save
  project. No dirty tracking anywhere: switching selection
  reloads from disk and discards edits.
- With no project selected, the no-project branch clears the
  text fields and notes but leaves the spinboxes, combos, and
  method showing values (`_show_project_detail`, `gui.py:506`).

### Train panel, v0.2 (`gui.py:759-915`)

- Dataset row: `Pick dataset file` (file picker, sets the
  Dataset field without saving) and `Use sample dataset` (sets
  `sample-tool-calls.jsonl`, calls `save_project`, logs "Save
  is done").
- `Start training` / `Pause` / `Resume`: Pause starts disabled;
  during a run Start and Resume disable and Pause enables.
  `start_training` (`gui.py:803`) checks for a selection, checks
  training deps (missing deps → hint in the log + status), saves
  the form, then starts a `TrainWorker`.
- Progress bar + loss label (`Step N / total — loss x.xxxx`),
  driven by the worker's `progress` signal.
- Checkpoints list (max height 90): `step N loss x.xxxx` per
  checkpoint from `list_checkpoints`; display-only, no
  selection handler.
- `Export GGUF` and `Run refusal probe`: each starts a generic
  `JobWorker` (thread) and logs its finish message. No progress
  signal on jobs, no guard against concurrent jobs.
- Training log: read-only `QPlainTextEdit`, minimum height 120.
  `refresh_train_panel` (`gui.py:759`) reloads it from the
  project's `train_log.jsonl` (last 30 lines) on every project
  selection — except mid-run, when it leaves the live log alone.
- `TrainWorker` (`gui.py:104`) runs `train_project` off the GUI
  thread and talks to the window only through signals; errors
  become `finished(False, message)`, never a crash.
- `closeEvent` (`gui.py:916`): if training is running, requests
  a stop and waits up to 15 seconds on the GUI thread. The job
  worker is not waited on.

### Dialogs

- New Profile: `NewProfileDialog` (`gui.py:62`), a plain
  `QWidget` — Name, Display name, Role (editable combo, 8
  suggestions), Ollama tag (editable combo fed from Ollama on
  construct, `gui.py:78`), Base ref, Create / Cancel. Opened
  by `new_profile` (`gui.py:596`) with `WindowModal` modality,
  resized to 420x320, shown — no centering, no default button,
  no singleton guard. Its docstring says it is "kept a QWidget
  so tests can drive it without a modal loop".
- New / Rename project and Rename profile: `QInputDialog.getText`
  prompts (real modal dialogs, Enter accepts).
- Delete profile/project: `QMessageBox.question` with Yes/No;
  proceeds only on Yes.
- Errors: `_warn` (`gui.py:402`, `QMessageBox.warning`) for
  `StellaError`s; the status bar for load failures. Anything
  that is not a `StellaError` escapes the handler uncaught.

### Tests covering the GUI

- `test_gui.py` (13 tests): three panes open, role in the list,
  detail fills from selection, save profile/project write
  through, empty-store window, no `&` in visible labels, frame
  grab, status-bar-only regression, Train panel widgets exist
  (Pause disabled), Start-without-deps logs the install hint,
  sample dataset sets the ref, progress updates.
- No test covers: the New Profile dialog (type, modality,
  Enter/Escape, position), selection-driven button states,
  dirty tracking, the Ollama fetch count, status-message
  overwrites, bad-settings detail fill, concurrent jobs,
  close-during-job, stale progress/loss, or any export/import
  button drive (audit #3's finding, unchanged in v0.2).

## 2. Strengths

1. **Training is genuinely worker-threaded.** Probed with a
   fake run: progress reached 2/4 mid-run, the loss label
   updated per step, and the window processed input throughout
   (D12). The run never blocks the UI thread.
2. **Pause works.** The stop request is honored by the loop,
   the log says "Pausing after this step (checkpoint will
   save)...", and the buttons restore on finish (D17/D18).
3. **The single-status-surface fix held.** No duplicate label
   reappeared in v0.2; the regression test still pins it.
4. **No bare `&` anywhere.** Checked every QLabel, QPushButton,
   and QComboBox item in the live window: zero (F1). The Qt
   mnemonic trap from the MIMIK lesson is avoided.
5. **Tab order follows the visual layout.** Focus-chain probe:
   profile list → its buttons → project list → its buttons →
   detail fields top to bottom, in order.
6. **Arrow keys work in the lists** (F3), and the first profile
   and project auto-select, so the window is usable without
   touching the mouse.
7. **Buttons never clip at minimum size.** At 900x540 every
   pane button fits its text (A10); the detail pane absorbs
   the shrink and stays usable (screenshot).
8. **The window fits his screen.** 1100x680 inside 1366x768
   with room to spare (A11).
9. **The offline Ollama path degrades gracefully.** With
   Ollama down, the dialog says plainly "Ollama is not
   answering — type the tag by hand", and the detail combo
   keeps the stored tag (dialog screenshot).
10. **Checkpoints read well.** `step 10 loss 2.1234` per row
    (D23), and the log tail is capped at the last 30 lines
    (D25) instead of dumping the whole file.
11. **The standard dialogs behave.** Enter accepts in the
    `QInputDialog` prompts (C7) — only the custom New Profile
    form breaks the pattern (W1).
12. **Delete asks first**, naming the profile/project and
    saying it cannot be undone (though see W4 for what Enter
    does in that dialog).
13. **Start-without-deps fails safe.** No worker starts, the
    log names the missing packages and the exact install
    command, and the status bar points at the log (D9).

## 3. Weaknesses (all verified)

### W1 — The New Profile "dialog" is not a dialog at all (P0)

`NewProfileDialog` is a plain `QWidget` with a parent and no
`Qt.Window` flag (`gui.py:62`). Probed on the real path
(`win.new_profile()`): `isWindow()` is False, geometry is
(0, 0, 420, 320) **in parent coordinates** — it renders as a
frameless, background-less form smeared over the top-left of
the main window, its labels overlapping the header and both
lists (screenshot `/tmp/gui-audit-dialog-real.png`, eyeballed).
The `WindowModal` flag (`gui.py:598`) does nothing on a
non-window: probed, the profile selection changed behind the
open "dialog". Enter does nothing (no default button, C2/C3),
Escape does nothing (C4), it is not centered (C5), and two can
be opened at once, stacked on top of each other (C6). The
primary creation flow in the program is visually broken and
behaves like nothing else in the window. (This corrects A1-U3,
which called it "a separate 420x320 window".)

### W2 — Start training ignores a failed save (P0)

`start_training` calls `self.save_project()` (`gui.py:823`)
and never checks whether it worked. Probed: with learning
rate `abc`, the warning dialog appeared **and the training
worker started anyway** (D21) — training on the stale on-disk
settings while the user just saw an error about the settings
they meant to use. The same unchecked save sits in
`use_sample_dataset` (`gui.py:795`): with a bad LR the warning
appeared and the log still claimed "Save is done" (D22) — and
with no project selected at all, the same "Save is done" line
is logged although nothing was saved (D7).

### W3 — The training log is wiped the moment a run finishes (P0)

`_on_train_finished` (`gui.py:850`) appends "Trained N
steps." to the log, then calls `refresh_train_panel`
(`gui.py:759`), which overwrites the log widget from
`train_log.jsonl` on disk. Probed: after a fake run finished,
the log was **empty** (D14) — the whole run record, finish
message included, erased. With a real run the file exists, so
instead of a blank log the user gets the raw JSONL records
(`{"epoch": 1, "loss": ..., "lr": ..., "step": ..., "type":
"step"}`, `train.py:511-513,666`) in place of the friendly
"step 3/4 loss 2.1000" lines they watched during the run
(mechanism probed in D25: the widget shows the file's last 30
lines verbatim). Either way the readable run record is gone
the moment the run ends.

### W4 — Enter in the delete confirm deletes (P0)

Probed with the real `QMessageBox.question` call and a timer
driving the modal loop: focus lands on the **Yes** button and
pressing Enter returns Yes (C8). The dialog's own text says
the delete "cannot be undone" — and delete is unrecoverable
(A1-W5, A2-W8: one dialog, then `rmtree`). A single Enter
keypress, the key every other dialog in the program trains
the user to press to accept, destroys a profile and all its
projects, or a project and its checkpoints.

### W5 — Unsaved edits are silently discarded on switch (P0)

Audit #2's W1, re-verified in v0.2 (E6): typed notes and a
changed display name, switched projects and back — notes
reverted to the saved text, display name reverted to the slug.
There is still no dirty tracking, no asterisk, no prompt, no
auto-save, in either detail panel. The completion path adds a
second trigger: `_on_train_finished` refreshes the projects,
which reloads the detail from disk and discards any edits the
user made during the run (same reload path as E6, code
`gui.py:850-857`). One fix must cover both panels (merged
task list T3).

### W6 — Bad settings abort the detail fill mid-way (P1)

`_show_project_detail` converts settings with bare `int(...)`
(`gui.py:529-533`) and no guard. Probed: a project whose
`project.json` says `rank: "high"` — selecting it raised
`ValueError` out of the signal handler (traceback printed to
stderr by Qt) and left the panel **mixed**: display name and
dataset showed the new project, while learning rate, epochs,
batch, seq len, metamorph, and notes still showed the previous
project's values (E8). The user now sees one project's
settings labeled as another's — and clicking Save writes the
mixed form back to disk, corrupting the project with the other
project's values (`save_project` reads the form
unconditionally, `gui.py:560`). The home is meant to be
hand-editable, so a mistyped value in the JSON turns a
selection click into a corruption vector.

### W7 — Every profile click re-fetches Ollama, on the UI thread (P1)

Audit #1's W4, unchanged in v0.2. `_show_profile_detail`
calls `list_models()` synchronously on every selection
(`gui.py:483`), with no cache. Probed against a counting fake
server: 2 selections = 2 fetches (B7); with a 1.2-second
server delay, a selection click blocked for 1.39 seconds (B8).
The New Profile dialog fetches again on construct
(`gui.py:78`, B9). On a swapping 8 GB box with a slow Ollama
startup, clicks can feel dead for up to the 2-second timeout.

### W8 — A bad import crashes silently in the window (P1)

Audit #3's W2, re-verified in v0.2 (E5): importing a package
whose `settings` is a string raised a raw `ValueError` out of
`import_package` (`gui.py:734`, which catches only
`StellaError`) — **no warning dialog appeared at all**, and
the orphan empty profile the failed import left on disk was
invisible in the list (refresh runs only on the success path).
The window's face of the trust-boundary crash is total
silence. The root fix is A3-D2/D3 (validate the manifest,
atomic import); the window also needs to catch broadly and
refresh on failure.

### W9 — No concurrency guards on jobs (P1)

Probed with slow fake jobs: starting the refusal probe while
a GGUF export was running started a second `JobWorker`
alongside the first (D27) — and starting a GGUF export while
training was running started it too (D28). Each start
overwrites `self._job_worker`, so the first job is orphaned
from the window's handle (its finish signal still fires, but
nothing tracks it). On 8 GB, a probe loading a model while a
training run holds its weights is a real OOM shape, and the
window does nothing to prevent it.

### W10 — Closing mid-job destroys the running thread (P1)

`closeEvent` (`gui.py:916-919`) waits for the *train* worker
only. Probed in a separate process: closing the window during
a GGUF export returned in 0.05s and Qt printed `QThread:
Destroyed while thread '' is still running` — the worker was
destroyed mid-flight, which Qt documents as a programming
error that can crash. Closing during a training run whose
worker ignores the stop request froze the UI for the full
15.07-second wait and then printed the same destroyed-thread
warning anyway. The 15-second freeze has no feedback at all:
the window just stops responding to a close click.

### W11 — Progress and loss are stale per project (P1)

`refresh_train_panel` never touches the progress bar or the
loss label (except setting "Pick a project to train." when
nothing is selected). Probed: after a run on `tool-calls`,
switching to `short-replies` — never trained — still showed
the run's progress and loss (D19/D20). The Train-panel
screenshot shows the contradiction at its worst: a **25%
progress bar** above the text "Pick a project to train."
with no project selected at all. The panel reports another
project's training as if it were this one's.

### W12 — Switching projects mid-run mixes the panels (P1)

Probed: start a run on `tool-calls`, switch to
`short-replies` mid-run — the checkpoint list rebuilt to the
new project's (empty) list while the progress bar and loss
label kept showing the running project's values (D26). The
`refresh_train_panel` early return ("never wipe the live log
mid-run", `gui.py:759`) protects the log but not the rest of
the panel, so mid-run the Train panel is half one project,
half another.

### W13 — Settings are editable and saveable during a run (P1)

Probed: mid-run, the rank spinbox accepted 16 and Save wrote
it to disk (D13). The running worker already loaded its
config, so the saved settings no longer describe the run in
progress — and the next run will use settings the user set
while watching the previous one. Combined with W5, edits made
during a run that are *not* saved are discarded by the
completion refresh.

### W14 — With no project selected, the panel shows settings anyway (P2)

The no-project branch of `_show_project_detail`
(`gui.py:506`) clears the text fields and notes but leaves
the spinboxes, the method combo, and the metamorph combo
showing values. Visible in the 1100x680 screenshot: with
`empty-profile` selected (no projects), the panel shows
Method `lora`, rank 8, epochs 3, batch 1, seq 1024 — settings
for a project that does not exist — while Learning rate sits
empty (it was cleared). `Save project` stays enabled and
clicking it silently does nothing. The panel state does not
reflect the selection state.

### W15 — The requested splitter sizes are not honored (P2)

`splitter.setSizes([260, 200, 640])` (`gui.py:270`) produced
`[270, 273, 531]` (A5): the middle pane cannot be 200px wide
because its three buttons need ~273px, so the detail pane
loses ~110px to the button rows. At minimum window size the
detail pane shrinks to ~331px. The layout's numbers are
aspirational; the button rows set the real floor.

### W16 — Both list panes can be dragged away entirely (P2)

Probed: `setSizes([0, 0, 1100])` collapsed both the profile
and project panes to width 0 (A12). `childrenCollapsible`
defaults to true, so a stray drag can lose both lists with no
obvious restore — the handles are still there, but a user who
has never seen a collapsed splitter has no reason to know
that.

### W17 — No per-profile project memory (P2)

`_on_profile_selected` resets `_current_project` to None
(`gui.py:467-473`), so returning to a profile always lands
on its first project. Probed (corrected): select
`tool-calls`, switch profiles, switch back — the window
shows `short-replies` (row 0), not the project the user was
working on. The first B6 probe passed by coincidence (row 0
happened to be the project under test); the corrected probe
confirms there is no memory.

## 4. UI flaws (verified)

- **U1 — Long rows truncate with no way to read them.**
  Audit #1's U1, unchanged in v0.2. Probed: the MiniCPM5 row
  is 343px of text in a 250px pane (B3), and the item has no
  tooltip (B4). The 1100x680 screenshot shows it plainly:
  `MiniCPM5 Driver [driver] — maternion/min...`, with a
  horizontal scrollbar as the only escape. Hovering tells
  you nothing.
- **U2 — Notes and the entire Train panel are below the fold.**
  Audit #2's U2, worse in v0.2. Probed geometry at 1100x680:
  detail content is 1289px tall in a 567px viewport (A6);
  the Notes editor starts at y=578, `Start training` at
  y=758, the progress bar at y=789, the Training log at
  y=996 (A7–A9). Only the "Notes" header peeks out at the
  bottom of the default window (screenshot). The primary
  action of the v0.2 release — Start training — needs a
  scroll on every visit.
- **U3 — Confirmations are overwritten before they can be
  read.** Audit #3's U1, re-verified (E2): after a successful
  import the status bar reads "Profile: … — project: …" —
  the "Imported …" message never survives its own refresh.
  Training has the same shape: `_on_train_finished` says
  "Trained N steps." and then `refresh_projects` overwrites
  it with the selection message (D15). Export gets a dialog;
  import and training-done get messages that erase
  themselves.
- **U4 — Buttons are enabled with nothing to act on, and
  the failures are inconsistent.** With an empty store, every
  action button is enabled (D2): Start, Resume, Export GGUF,
  Run refusal probe, Export, Import, Rename, Delete. Clicking
  Rename/Delete/Save with no selection does *nothing at all*
  — no dialog, no status change (D4) — while Export and New
  project warn (D5/D6). The same dead click teaches two
  different lessons depending on which button it was.
- **U5 — Empty panes give no guidance.** A profile with no
  projects shows a blank white list (screenshot); an empty
  store shows two blank white lists. The only voice is the
  status bar ("Pick a profile to begin."). Nothing in the
  panes says what to do next.
- **U6 — No window icon.** `windowIcon().isNull()` is true
  (A3); the title bar shows Qt's default icon, although the
  gold-star icon ships in `assets/` (SVG + PNGs) and the
  app-menu entry uses it. The running window does not look
  like Stella.
- **U7 — One tooltip in the entire window.** Probed: exactly
  one widget has a tooltip — the metamorph combo (F2). Rank,
  learning rate, epochs, batch, seq len, the dataset field,
  and every button have no explanation of what they do or
  what sane values look like (audit #2's U7, unchanged).
- **U8 — The missing-deps hint goes where the user cannot
  see it.** Start-without-deps writes the install hint to
  the Training log (D9) — which sits at y=996, below the
  fold (A8). The status bar says "see the Train log", but
  the user has to know to scroll for it; on first run, the
  most likely first-run failure hides its own fix.
- **U9 — No double-click anywhere.** Neither list responds
  to a double-click (F4): no double-click to rename, no
  double-click to open, no double-click on a checkpoint to
  see it. Every action is a button click away, and the most
  obvious gesture does nothing.

## 5. Gaps (against the design intent)

- **G1 — No geometry or state persistence.** No `QSettings`
  anywhere: window size, splitter positions, and the last
  selection are forgotten on every launch. The user
  re-arranges the window every time they open it.
- **G2 — No keyboard shortcuts.** No Ctrl+S to save, no
  Ctrl+N for a new profile/project, no mnemonics on any
  button (grep: no `QShortcut`, no `setShortcut`). The
  window is mouse-only except for list arrows and Tab.
- **G3 — The checkpoint list is display-only.** Clicking a
  checkpoint does nothing (D24): no resume-from-checkpoint,
  no delete, no disk usage, no detail. The Train panel owns
  checkpoints now (audit #2's W15, expected in v0.1) but
  still cannot act on them.
- **G4 — No progress or cancel for GGUF/probe jobs.**
  `JobWorker` has no progress signal — a multi-minute GGUF
  export shows only log lines, and there is no way to stop
  it once started. Training has Pause; jobs have nothing.
- **G5 — No status display anywhere.** Audit #2's W5/G1,
  window face: no widget shows or changes a project's
  status, in the list or the detail panel. A project that
  trained, failed, or exported looks exactly like a draft.
- **G6 — No health indicator.** Audit #1's W11, window
  face: a profile pointing at a missing model, a profile
  with no tag, and a good profile are visually identical
  rows. Nothing in the window says whether the base exists.
- **G7 — No single-instance guard.** `main()` (`gui.py:924`)
  starts a window with no lock file or single-application
  check (code citation). Two Stella processes could open
  the same home and write the same manifests over each
  other.

## 6. Innovation and design suggestions

- **D1 — Make New Profile a real QDialog.** Modal, centered
  on the parent, Create as the default button (Enter works),
  Escape closes, and one instance at a time. The test
  concern in the docstring is real — drive it with
  `QTest` + a timer, the way this audit drove the modal
  dialogs — but a test convenience must not ship as a
  broken dialog. (W1)
- **D2 — Gate Start and sample-dataset on save success.**
  Have `save_project` return whether it saved, and refuse
  to start training — or to claim "Save is done" — when it
  did not. A failed save must stop the action that depends
  on it. (W2)
- **D3 — Keep the live training log.** Do not let the
  finish refresh overwrite the log the user watched: keep
  the in-memory lines, and when reloading from
  `train_log.jsonl`, render the JSON records as the same
  friendly "step N/total loss x.xxxx" lines instead of raw
  JSON. (W3)
- **D4 — Delete confirms default to No.** Make No the
  default button so Enter never deletes, and add the trash
  from A1-D6 so a confirmed delete is still recoverable.
  (W4)
- **D5 — Dirty tracking, or auto-save on switch.** Shared
  with A2-D1 / merged task list T3: mark edited fields,
  prompt on leaving with unsaved edits, or save on switch —
  covering both detail panels and the completion refresh.
  (W5, W13)
- **D6 — Fill the detail panel defensively.** A setting of
  the wrong type falls back to its default (and the panel
  says so) instead of aborting the fill mid-way. Never let
  a read error become a mixed panel, and never let a mixed
  panel be saved. (W6)
- **D7 — Cache the model list; fetch off the UI thread.**
  Shared with A1-D5: fetch once at startup, refresh on
  demand, never block a click on the network. (W7)
- **D8 — Handle import failure in the window.** Catch
  broadly in `import_package`, refresh the lists on failure
  so an orphan is visible, and say what happened — while
  A3-D2/D3 fix the root cause (validate the manifest, make
  import atomic). (W8)
- **D9 — One job at a time.** A single running-job slot:
  GGUF export and the probe disable each other and disable
  during training, with the status bar saying what is
  running. On 8 GB, two model-loading jobs at once is a
  crash waiting for a reason. (W9)
- **D10 — Close waits for every worker, without freezing.**
  Wait for the job worker too; show "Stopping training…"
  and close when the thread ends instead of blocking the UI
  thread for 15 seconds; never destroy a running thread.
  (W10)
- **D11 — Reset progress/loss per project; pin the panel
  to the running project.** Selecting a project resets the
  bar and label to that project's state, and while a run is
  live the Train panel follows the running project (or says
  which project is running) instead of mixing panels.
  (W11, W12)
- **D12 — Lock the settings during a run.** Disable the
  project form and Save while training runs — or warn that
  a mid-run save does not affect the running config. The
  form should not offer to change a run in progress. (W13)
- **D13 — Clear the whole panel with no selection.** The
  no-project branch should reset spinboxes, combos, and
  method to blank/default and disable Save, so the panel
  never shows settings for a project that is not there.
  (W14)
- **D14 — Give the splitter honest minimums.** Set minimum
  widths on the panes (or drop the unachievable 200px
  request) and set `childrenCollapsible` to false, so a
  drag cannot lose a pane. (W15, W16)
- **D15 — Remember the project per profile.** Keep the last
  selected project for each profile and restore it on
  return, instead of always landing on row 0. (W17)
- **D16 — Tooltips where the text is cut or the meaning is
  not obvious.** Row tooltips with the full label; help
  text on rank, learning rate, epochs, batch, and seq len
  with sane ranges. (U1, U7; shared with A1-D10)
- **D17 — Put the Train panel above the fold.** Move Train
  above Notes, or give the detail pane a Train tab, or make
  the sections collapsible — the release's headline action
  should not need a scroll on every visit. (U2)
- **D18 — Status discipline: confirm after the refresh.**
  Say the confirmation *after* any refresh it triggers, or
  give import and training-done the same success dialog
  export already has. A confirmation the window erases
  itself is not a confirmation. (U3; shared with A3-D14)
- **D19 — Buttons follow the selection; panes explain
  themselves.** Disable actions with nothing to act on, in
  one `_update_actions` pass; put a one-line hint in an
  empty list ("No projects yet — New project to start").
  (U4, U5)
- **D20 — Window chrome pass.** Set the window icon from
  the shipped star art; persist size, splitter, and last
  selection with `QSettings`; add the two shortcuts that
  matter (Ctrl+S save, Ctrl+N new). (U6, G1, G2)
- **D21 — Checkpoint actions and job progress.** Resume
  from a selected checkpoint, delete a checkpoint, disk
  usage in the list; a progress signal (or at least an
  indeterminate bar + a stop button) on `JobWorker`.
  (G3, G4)
- **D22 — Show status and health.** A status line in the
  project row and detail panel, driven by training and
  export (shared A2-D5); a health badge per profile row
  from the cached model list (shared A1-D1). (G5, G6)
- **D23 — Single-instance guard.** A lock file (or
  `QtSingleApplication`-style check) so a second launch
  raises the running window instead of opening a second
  writer on the same home. (G7)
- **D24 — Double-click does the obvious thing.** Rename
  on a list double-click; checkpoint detail on a checkpoint
  double-click. (U9)
- **D25 — Put the missing-deps hint where the user can see
  it.** A warning dialog, or auto-scroll the detail pane to
  the log when the hint is written — not a status line
  pointing at a below-fold log. (U8)
